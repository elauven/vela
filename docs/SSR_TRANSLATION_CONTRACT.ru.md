# Контракт трансляции JavaScript в Go для SSR и ручных реализаций на Go

Статус: нормативный, реализован в бете (2026-10-09). Владелец: задача 007;
семантика — задачи 028 и 043–046, host-привязки и клиентские границы — 030,
поставка — 048 и 049; бета-гейт — задача 031 ([SSR_GATE.md](SSR_GATE.md)).

Это русская версия `SSR_TRANSLATION_CONTRACT.md`. Идентификаторы правил
совпадают. При расхождении текстов нормативной считается английская версия;
изменения вносятся в обе версии одновременно.

Документ задаёт нормативный контракт того, как серверный рендеринг Vela
превращает JavaScript, выполняемый во время рендера, в Go, и как разработчик
предоставляет реализацию на Go для кода, который компилятор не транслирует.
`SSR.md` — обзор продукта. Если этот документ противоречит более раннему
дизайну (`archive/SSR_DESIGN.md`), приоритет у этого документа; заменённые
положения перечислены в §14.

У каждого правила есть стабильный идентификатор (`T-…`, `H-…`, `D-…`, `V-…`).
Тесты, диагностики и отчёты по задачам должны ссылаться на эти идентификаторы.

---

## 1. Зафиксированные продуктовые решения

- **P-1. Только Go.** Серверный рендеринг никогда не встраивает, не запускает
  и не вызывает JavaScript-движок. Всё серверное поведение — это
  сгенерированный Go, Go-runtime Vela и Go-код разработчика.
- **P-2. Транслировать то, что можно сделать точным; остальное делегировать
  явно.** У каждого места JavaScript-кода, выполняемого на сервере, ровно один
  исход (§4). Компилятор транслирует место, только если результат на Go
  наблюдаемо идентичен результату JavaScript на всей области входных значений.
  Иначе разработчик предоставляет Go-реализацию (`server-host`), явно
  откладывает место до браузера (`client-deferred`) или получает диагностику с
  конкретным способом исправления.
- **P-3. Никаких тихих расхождений.** Успешная сборка означает одно из трёх:
  доказанную семантическую эквивалентность, объявленную разработчиком
  host-реализацию или объявленную разработчиком клиентскую границу.
  Приближённая трансляция никогда не является неявным исходом.
- **P-4. Только Go AST.** Сгенерированный Go строится из `go/ast`, печатается
  через `go/format` и проверяется `go/types` (существующий инвариант Phase 0).
- **P-5. Только кэшированные AST.** Транслятор работает с JS AST, которыми
  владеет парсер; он никогда не разбирает исходный текст повторно.

## 2. Серверная область выполнения

Транслятор отвечает только за код, который выполняется во время серверного
рендера. Всё остальное остаётся JavaScript и для SSR не анализируется.

**T-2.1 Корни области.** Серверная область компонента состоит из:

1. значений по умолчанию пропов `export let`;
2. инициализаторов `$state` / `$state.deep` / `$bindable`;
3. выражений `$derived`;
4. выражений шаблона: в тексте, атрибутах, директивах `class:` / `style:`,
   условиях `{#if}`, коллекциях и ключах `{#each}`, выражениях `{#key}`,
   операндах `{#await}` и пропах, передаваемых дочерним компонентам;
5. обычных `const` / неизменяемых `let` верхнего уровня, которые читаются из
   пунктов 1–4;
6. транзитивного замыкания функций и импортированных символов, вызываемых из
   пунктов 1–5, включая функции из локальных модулей `.js`.

**T-2.2 Исключения из области.** Следующее никогда не транслируется, не
проверяется на типы для SSR и не порождает SSR-диагностик: обработчики
событий, `$effect`, `onMount` / `onDestroy`, обратная запись привязок,
`bind:this` и любые функции, достижимые только из них. Обработчик, который не
входит в область, не может заблокировать SSR своего компонента.

> Следствие: текущие ошибки static event bridge (`VELA-SSR-EVENT-REACTIVE`) не
> должны выдаваться для компонента с исполняемой гидратацией. Компонент, у
> которого не прошла гидратация, сообщает причину гидратации (§10), а не
> причину, связанную с обработчиком событий.

**T-2.3 Отчёт по области.** Для каждого места в области компилятор
записывает: ID места, диапазон в исходнике, исход (§4), уровень (§5.4),
семантический тип и, для делегированного места, host-символ или границу.
Эта запись — единственный источник истины для генерации кода, диагностик,
`--ssr-report` (§10.4) и метрик по корпусу.

## 3. Конвейер

```
JS AST (кэш) ──► Анализ области и областей видимости ──► Серверный IR (типизированный, исход на каждое место)
                                                              │
                     Анализ host-пакетов (go/types) ──────────┘
                                                              ▼
                                                     Понижение в Go AST ──► go/format ──► go/types
```

- **T-3.1** Решения (исход, тип, уровень, host-привязка) принимаются один раз,
  при построении серверного IR. Понижение в Go только потребляет IR; оно не
  должно само классифицировать, выводить типы или отклонять конструкции.
- **T-3.2** Каждый узел IR сохраняет диапазон в исходнике и ID места в
  области, чтобы и ошибка во время выполнения, и диагностика указывали на
  исходную позицию в `.vela` / `.js`.
- **T-3.3** Построение IR детерминировано: одинаковые входные данные дают
  побайтно одинаковый Go.
- **T-3.4** Host-пакеты анализируются только через `go/parser` и `go/types`.
  Компилятор никогда не собирает и не выполняет Go-код разработчика во время
  компиляции.

## 4. Исходы для места и порядок разрешения

| Исход | Сервер | Клиент |
| --- | --- | --- |
| `server-native` | Сгенерированный Go вычисляет место. | Гидратация принимает результат; дальнейшие обновления используют исходный JS. |
| `server-host` | Сгенерированный Go вызывает Go-функцию разработчика. | Как выше. |
| `client-deferred` | Детерминированный fallback внутри собственного диапазона маркеров. | Гидратор вычисляет исходный JS и заменяет диапазон. |
| `unsupported` | Сборка падает с диагностикой и позицией. | — |

**T-4.1 Порядок разрешения** для вызова функции или импортированного символа:

1. объявленная host-реализация (§8), даже если нативная трансляция возможна —
   явный выбор разработчика побеждает;
2. нативная трансляция, если каждая конструкция в теле функции допущена
   (§6, §7), а её типы доказуемы на каком-либо уровне (§5);
3. явная клиентская граница, охватывающая место (§9);
4. иначе `unsupported` с диагностикой, требуемой §10.

**T-4.2** `client-deferred` никогда не выбирается неявно.

**T-4.3** Место, значение которого управляет структурой (`#if`, `#each`,
`#key`, `#await`, выбор компонента), может быть `server-native` или
`server-host`, но `client-deferred` — только через явную структурную границу.

## 5. Модель значений и типы

### 5.1 Правило JSON-представления

**T-5.1** Видимая из JavaScript форма любого Go-значения, попадающего в
серверную область (пропы, результаты host-функций, константы host-пакетов),
в точности совпадает со значением, которое браузер получает из
`JSON.parse(json.Marshal(v))`.

Это одно правило фиксирует имена свойств (теги `json`), скрытые поля
(`json:"-"`), `omitempty`, `time.Time` (строка ISO), `[]byte` (строка base64),
`nil`-указатель (`null`) и порядок ключей объекта. Оно также гарантирует, что
сервер вычисляет те же данные, которые клиент получит в payload гидратации.

- **T-5.1a** Обращение к свойству `user.name` у Go-структуры разрешается в
  поле, чьё JSON-имя при кодировании — `name`. Методы Go никогда не видны.
- **T-5.1b** Go-значение, которое нельзя закодировать в JSON (func, chan,
  complex, цикл), не может попасть в область. Для типов пропов и результатов
  host-функций это проверяется через `go/types`, и сборка падает
  (`VELA-SSR-HOST-SIG` / `VELA-SSR-PROPS`).
- **T-5.1c** Перечисление ключей объекта (`Object.keys`, `for…in`, spread,
  вывод JSON) следует порядку JavaScript поверх JSON-представления:
  ключи-целые числа в порядке возрастания, затем остальные ключи в порядке
  JSON-текста. `encoding/json` пишет ключи map, отсортированными как строки
  (`"10"` перед `"2"`), а JavaScript перечисляет `"2"` перед `"10"`.

### 5.2 Семантические типы

IR использует типы уровня JavaScript:

`undefined`, `null`, `boolean`, `number`, `string`, `Array<T>`,
`Object{field: T…}` (закрытая форма), `Record<T>` (открытый объект со
строковыми ключами), `Function(sig)`, их объединения и `unknown`.

Источники, по убыванию приоритета: типы пропов разработчика в `*_props.go` и
сигнатуры host-функций (Go имеет решающий голос), JSDoc `@type` / `@param` /
`@returns`, литеральные инициализаторы, поток значений через объявления и
`return`, типы результатов допущенных встроенных функций.

### 5.3 Представление в Go

| Семантический тип | Представление в Go |
| --- | --- |
| `number` | Всегда `float64`. Целочисленные типы Go принимаются на границе и расширяются. |
| `string` | Go `string` с UTF-8; операции над UTF-16 — см. §6.3. |
| `boolean` | `bool` |
| `null` | `nil` |
| `undefined` | `vela.Undefined()` (существующий sentinel; отличается от `nil`) |
| `Array<T>` | `[]T`, если `T` точный, иначе `[]any` |
| `Object{…}` из Go | структура разработчика (читается через JSON-представление) |
| `Object{…}` / `Record`, созданные транслированным кодом | `*vela.Object` (с сохранением порядка вставки); никогда не `map[string]any` |
| объединение / `unknown` | `any`, содержащий значение из области JSON-значений |

**T-5.3a** Внутри транслированного кода `number` остаётся `float64`, даже
если значение целое. Преобразование в целое происходит только на явной
границе (индексация, целочисленный параметр host-функции) и проверяется
(§8.4).

### 5.4 Два уровня, одна семантика

- **Типизированный уровень**: типы доказаны точно; понижение в прямой Go
  (`a + b` для `float64`, `len(s)` для `[]T`).
- **Динамический уровень**: тип `unknown` или объединение; понижение в
  runtime-хелперы с полной семантикой JavaScript над областью JSON-значений
  (`vela.Add(a, b)`, `vela.Get(v, "k")`, `vela.Less(a, b)`).

**T-5.4a** Выбор уровня — только оптимизация. Для каждой допущенной
конструкции типизированное и динамическое понижение обязаны давать одинаковый
наблюдаемый результат; оракулы (§11) проверяют оба уровня.

**T-5.4b** Отсутствие точного типа само по себе никогда не причина для
`unsupported`. Ошибки вида «relational operator requires two known numbers»
заменяются понижением в динамический уровень.

**T-5.4c** Каждый динамический хелпер тотален на области JSON-значений плюс
`undefined`: он возвращает значение или JavaScript-исключение (§6.5) и
никогда не паникует.

## 6. Семантика выражений

### 6.1 Порядок вычисления

- **T-6.1a** Операнды, аргументы и элементы объектов/массивов вычисляются
  слева направо, каждый ровно один раз.
- **T-6.1b** `&&`, `||`, `??`, `?:` и `?.` вычисляются по короткой схеме:
  невыбранный операнд никогда не вычисляется (R1). Значение null или
  undefined перед `?.` завершает всю цепочку, её чтения членов и вызовы,
  как в `a?.b.c()` и `f?.(x)`; скобки завершают цепочку. Восстановление
  после паники не является реализацией короткой схемы.
- **T-6.1c** Вызов host-функции выполняется ровно один раз на каждое
  вычисление места вызова, в той позиции, где его вызвал бы JavaScript; он
  никогда не выносится, не кэшируется между местами и не выполняется
  спекулятивно.

### 6.2 Операторы

| Конструкция | Контракт |
| --- | --- |
| `+` | Правило JS `ToPrimitive` / строка-или-число, на обоих уровнях. |
| `- * / % **` | IEEE-754 `float64`; `%` — остаток JS (знак делимого); `**` следует граничным случаям `Math.pow`. |
| `< <= > >=` | Сравнение чисел; сравнение строк по кодовым единицам UTF-16, если оба операнда строки; иначе абстрактное реляционное сравнение JS. |
| `===` / `!==` | Строгое равенство JS (`NaN !== NaN`, `+0 === -0`); объекты сравниваются по идентичности. |
| `==` / `!=` | Допускается только с литералом `null` / `undefined` в одном из операндов (`x == null`). Все прочие случаи — `unsupported` с подсказкой использовать `===`. |
| `!`, `typeof`, унарные `-`/`+` | Семантика JS; `typeof` для значения из Go следует JSON-представлению. |
| `?.`, `??` | Допускаются на обоих уровнях. |
| шаблонные строки | Контракт преобразования в текст (`SSR.md`, раздел «Text conversion»). |
| литералы массивов/объектов, spread массивов/объектов, вычисляемые ключи `{ [k]: v }` | Допускаются; объекты строят `*vela.Object` с порядком вставки; вычисляемый ключ вычисляется до значения и преобразуется по ToPropertyKey. |
| стрелочные функции | Допускаются как колбэки допущенных встроенных функций и как локальные значения; замыкания могут читать захваченные привязки. |
| `k in o` | Допускается для объектов и массивов (собственные свойства и свойства прототипов, как в Node 24); примитив справа выбрасывает `TypeError`. |
| запятая `(a, b)`, `void e` | Допускаются; операнды вычисляются слева направо со своими эффектами; `void` даёт `undefined`. |
| `new Error(m)`, `new TypeError(m)`, `new RangeError(m)` | Допускаются; создают объекты ошибок с `name` из прототипа и неперечисляемым `message`; преобразование в текст — `Error.prototype.toString`. |
| прочие `new`, `this`, `class`, геттеры/сеттеры, `delete`, `instanceof`, литералы регулярных выражений, теговые шаблоны | В v1 — `unsupported`. |

### 6.3 Строки

- **T-6.3a** `length`, индексация, `charAt`, `charCodeAt`, `slice`,
  `substring`, `at`, `padStart`/`padEnd`, позиции `indexOf` и порядок
  сортировки используют кодовые единицы UTF-16. Пример: `"😀".length` в JS
  равно 2, а `len` в Go — 4.
- **T-6.3b** Одиночный суррогат, получившийся в результате операции,
  выводится в HTML как U+FFFD. Это единственное объявленное расхождение в
  кодировке; у него есть строка оракула, и dev-проверка гидратации (§11.3)
  считает такие значения равными.
- **T-6.3c** Смена регистра использует полный Unicode SpecialCasing, а не
  `strings.ToUpper`. Пример: `"straße".toUpperCase()` в JS даёт `"STRASSE"`,
  а `strings.ToUpper` — `"STRAßE"`. Варианты, зависящие от локали
  (`toLocaleUpperCase`), — только через host.

### 6.4 Числа в текст

- **T-6.4a** Преобразование числа в строку следует ECMAScript
  `Number::toString` (кратчайшее представление с точным обратным
  преобразованием; экспоненциальная форма с 1e21; `-0` печатается как `0`;
  `NaN`; `Infinity`).
- **T-6.4b** У каждой встроенной функции форматирования своё правило
  округления JS. Примеры, где нельзя использовать очевидный вызов Go:
  `(2.5).toFixed(0)` в JS даёт `"3"`, а
  `strconv.FormatFloat(2.5, 'f', 0, 64)` — `"2"`; `Math.round(-2.5)` в JS
  даёт `-2`, а `math.Round` — `-3`.

### 6.5 Исключения

- **T-6.5a** Операция, которая в JavaScript выбрасывает исключение (чтение
  свойства у `null`/`undefined`, вызов не-функции, `throw` в транслированной
  функции), порождает Go-ошибку типа `*vela.RenderError` с видом JS-ошибки
  (`TypeError`, `RangeError`, `Error`), сообщением и позицией места в
  исходнике. Рендерер возвращает эту ошибку.
- **T-6.5b** Индекс за пределами массива или отсутствующее свойство — не
  исключение: результат `undefined`, как в JavaScript. Сгенерированный код
  никогда не должен вызывать в Go панику index out of range или обращение к
  nil-map.
- **T-6.5c** Вывод, записанный до ошибки, не откатывается. Приложения,
  которым нужен ответ по принципу «всё или ничего», рендерят в буфер.
  Существующая предварительная проверка payload (`VELA-SSR-PROPS`) сохраняет
  свою более сильную гарантию. Рендер собирает вывод порциями (в
  `*bytes.Buffer` пишет напрямую) и записывает накопленное, когда
  возвращается внешний компонент, с ошибкой или без неё, поэтому writer
  получает те же байты за меньшее число вызовов.
- **T-6.5d** `try` / `catch` / `finally` следуют семантике JavaScript. `catch`
  получает выброшенные JS-значения, runtime-исключения JS (T-6.5a) и ошибки
  host (в представлении из T-7.4h). `finally` выполняется после обычного
  завершения, `return` и `throw`; `return` или `throw` внутри `finally`
  заменяет ожидающее завершение. Паники Go никогда не перехватываются.
- **T-6.5e** Только функции, которые могут выбросить исключение напрямую или
  транзитивно, понижаются с результатом `error`. Анализ исключений избавляет
  код, который не может выбросить исключение, от накладных расходов на
  проверку ошибок.

### 6.6 Чистота и детерминизм

- **T-6.6a Никаких внешних записей.** Код области не может записывать в
  состояние компонента, привязки уровня модуля, глобальные объекты, пропы и
  значения, которые он не создал сам. Нарушения — `unsupported`
  (`VELA-SSR-IMPURE`).
- **T-6.6b Локальные мутации разрешены.** Транслированная функция может
  изменять массивы и объекты, созданные ею самой в текущем вызове (например,
  `const out = []; out.push(x)`), и переприсваивать собственные `let`.
  Компилятор доказывает это локальным анализом выделений; общий escape-анализ
  не требуется.
- **T-6.6c Недетерминизм.** `Date.now()`, `new Date()`, `Math.random()`,
  `crypto.*`, `performance.now()`, `Promise.race` и `Promise.any` никогда
  не транслируются нативно. В
  инициализаторе `$state` они могут быть `server-host` (значение передаётся в
  payload). В `$derived` или выражении шаблона им нужен `client-deferred`,
  потому что клиент пересчитает значение и получит другое.
- **T-6.6d Порядок инициализации.** Значения пропов по умолчанию, затем
  инициализаторы `$state`, затем значения `$derived` вычисляются один раз в
  порядке объявления в скрипте — так же, как при инициализации на клиенте.
  `$state(prop)` и `$derived` поверх пропов и состояния — обычные допущенные
  места. Payload гидратации содержит вычисленные начальные значения, а не
  константы времени компиляции.

## 7. Операторы, функции и модули

### 7.1 Допущенные операторы (v1)

Объявления `const` / `let` (включая деструктуризацию массивов/объектов со
значениями по умолчанию и rest-элементами), rest-параметры, присваивание локальным привязкам, составное
присваивание, `++`/`--` для локальных привязок, `if`/`else`, `for (;;)`,
`for…of` по массивам и строкам, `while`, `do…while`, `break` / `continue`
(без меток), `return`, `throw`, `try` / `catch` / `finally` (T-6.5d),
`switch` с сопоставлением через `===`, вложенные объявления функций, блочная
область видимости, `async`-функции и `await` (§7.4).

Не допускаются в v1: метки, `for…in`, генераторы и асинхронные генераторы,
`for await`, классы, `with`, `eval`, `arguments`, всплытие `var` между
блоками, геттеры/сеттеры.

- **T-7.1a** Хелпер из нескольких операторов транслируется в Go-функцию, а не
  встраивается. Текущий встраиватель функций из одного `return` становится
  оптимизацией этого пути.
- **T-7.1b** Рекурсия разрешена. За завершимость отвечает разработчик, как и
  в JavaScript.

### 7.2 Функции и специализация

- **T-7.2a** Каждая транслированная JS-функция порождает по одной Go-функции
  на каждый различный кортеж семантических типов аргументов, встреченный в
  местах её вызова внутри области (мономорфизация), с детерминированными
  именами (`formatCurrency__num`, `formatCurrency__any`). Если число вариантов
  функции превысило бы 4, компилятор генерирует один вариант динамического
  уровня.
- **T-7.2b** Колбэки, передаваемые в допущенные встроенные функции массивов,
  понижаются в Go-замыкания или циклы; их параметры получают тип элемента.

### 7.3 Модули

- **T-7.3a** Локальные модули `.js`, импортируемые кодом области,
  транслируются по тем же правилам. Каждый модуль соответствует одному
  сгенерированному Go-пакету, повторяющему его путь в `server/modules/`.
  Функция, используемая несколькими компонентами, транслируется один раз.
- **T-7.3b** Код верхнего уровня модуля выполняется на сервере только для
  инициализации привязок `const` допущенными детерминированными
  инициализаторами. Любой другой побочный эффект верхнего уровня делает
  символы модуля из области `unsupported`, если они не привязаны к host.
- **T-7.3c** Импорты npm-пакетов никогда не транслируются. Их символы в
  области — `server-host` или `client-deferred`, иначе сборка падает.

### 7.4 Асинхронный код: синхронная модель выполнения

Единственная задача сервера — вернуть отрендеренный HTML, поэтому
асинхронный код выполняется за один синхронный проход.

- **T-7.4a Модель выполнения.** `async`-функция понижается в обычную
  Go-функцию, возвращающую `(T, error)`. `await e` вычисляет `e`; если `e` —
  промис, полученный из транслированного кода или host, `await` в этой точке
  возвращает его значение или выбрасывает его ошибку. В сгенерированном коде
  нет горутин, цикла событий и очереди микрозадач.
- **T-7.4b Значения-промисы.** Вызов `async`-функции без `await` в месте
  вызова создаёт уже завершённый `vela.Promise` (значение или ошибка).
  Допускаются: `.then`, `.catch`, `.finally`, `Promise.resolve`,
  `Promise.reject`, `Promise.all` и `Promise.allSettled`, вычисляемые в
  порядке элементов массива.
- **T-7.4c Объявленное отличие.** JavaScript чередует выполнение
  `async`-функций в точках `await`; синхронная модель завершает каждый вызов
  в порядке исходного кода. При T-6.6a (никаких внешних записей) и H-8.5b
  (детерминированные host) результаты идентичны. Единственное отличие —
  порядок вызова host-функций во времени, и host-функции не должны от него
  зависеть.
- **T-7.4d Не допускаются.** `Promise.race` и `Promise.any` (результат зависит
  от времени; используйте host или клиентскую границу), `setTimeout`,
  `setInterval`, `queueMicrotask`, `requestAnimationFrame`,
  `new Promise(executor)`, `for await`, асинхронные генераторы и `await`
  верхнего уровня в скрипте компонента (клиентский язык его не
  поддерживает).
- **T-7.4e Загрузка данных.** `fetch` и прочий браузерный ввод-вывод никогда
  не транслируются нативно. Загрузка данных на сервере — это host-функция: JS
  `loadUsers()` вызывает `fetch` в браузере, а её Go-реализация читает базу
  данных напрямую. H-8.5a применяется к полученному значению.
- **T-7.4f Блоки `{#await}`.** Если операнд `server-native` или
  `server-host`, сервер вычисляет его синхронно и рендерит ветку `then` со
  значением или ветку `catch` с ошибкой, но никогда `pending`. Завершённый
  snapshot (состояние плюс JSON-представление значения или ошибки; объект
  ошибки — в форме S-6.11, так как его JSON-представление `{}`)
  записывается в payload. Гидратация принимает завершённую ветку, и клиент
  не вычисляет операнд повторно при начальной гидратации; он вычисляет его
  заново, только когда меняются зависимости операнда. (Обязательное
  поведение: проверить текущий клиентский runtime и изменить его, если он
  выполняет операнд повторно.) Если операнд нельзя вычислить на сервере,
  весь блок `{#await}` должен находиться внутри блока `{#client}`; тогда
  сервер рендерит заглушку этой границы (T-9.1b). Snapshot, переданный через
  `RenderOptions.Await`, имеет приоритет над вычислением, и тогда операнд не
  вычисляется. Значения snapshot расширяются со строк до любых
  JSON-значений, удовлетворяющих T-5.1b.
- **T-7.4g Отмена.** Host-функции получают `ctx` рендера. Если `ctx`
  отменён, рендер возвращает `ctx.Err()` на ближайшем вызове host или точке
  `await`.
- **T-7.4h Раскрытие ошибок host.** Ошибка host попадает в JS-код (привязка
  `catch`, ветка `catch` блока `{#await}`) как объект ошибки с `name`
  `"Error"`. Её `message` — публичное сообщение, если в цепочке ошибок есть
  `vela.PublicError`; иначе — фиксированный текст `"Internal error"`, а
  исходная ошибка передаётся наблюдателю, заданному через
  `vela.WithErrorObserver(ctx, …)`. Причина: содержимое ветки `catch` и
  payload уходят в браузер, поэтому внутренний текст ошибок (SQL, пути к
  файлам) по умолчанию не должен утекать. Неперехваченная ошибка host
  по-прежнему роняет рендер с полной ошибкой, которая остаётся на сервере.

## 8. Host-реализации разработчика

### 8.1 Конфигурация проекта

`vela.ssr.json` в корне проекта (необязателен, пока не нужен host):

```json
{
  "module": "example.com/site/out/server",
  "host": {
    "dir": "ssrhost",
    "module": "example.com/site/ssrhost"
  },
  "runtime": {
    "module": "example.com/vela/ssr_runtime"
  }
}
```

`module` заменяет значение по умолчанию `--ssr-module`; флаг CLI остаётся
способом переопределения. `runtime.module` переопределяет путь импорта
Go-runtime (R-12.1b). `host.dir` — дерево Go-исходников, принадлежащее
разработчику. Компилятор его читает, но никогда не пишет, не форматирует и не
удаляет существующие файлы в нём (H-8.6).

### 8.2 Обнаружение и привязка

**H-8.2a Зеркальные пакеты.** Host-код для JS-файла лежит в пакете,
повторяющем путь этого файла:

| JS-символ | Каталог host-пакета |
| --- | --- |
| экспорт `formatCurrency` из `src/lib/format.js` | `ssrhost/src/lib/format/` |
| функция `embedUrl` внутри `src/blocks/VideoBlock.vela` | `ssrhost/src/blocks/videoblock/` |

**H-8.2b Явная директива.** Go-функция становится host-реализацией только
через комментарий-директиву с именем JS-символа:

```go
package format

//vela:host formatCurrency
func FormatCurrency(amount float64) (string, error) {
	// ...
}
```

Соглашения об именах сами по себе никогда не создают привязку. Благодаря
этому посторонний Go-код в дереве host остаётся инертным, а имя в Go может
отличаться от имени в JS.

**H-8.2c Устаревшие привязки.** Директива `//vela:host`, чей JS-символ
отсутствует в соответствующем исходнике, — ошибка сборки
(`VELA-SSR-HOST-STALE`), поэтому переименование в JS не может оставить
незаметно неиспользуемую реализацию.

**H-8.2d Дублирующиеся привязки.** Две директивы для одного JS-символа —
ошибка сборки.

**H-8.2e Цели привязки.** В v1 host-привязка указывает на именованную
функцию: экспорт модуля, объявление `function` верхнего уровня или
стрелочную функцию в `const` верхнего уровня в скрипте компонента. Чтобы
делегировать выражение, которое не является вызовом функции, разработчик
выносит его в именованную функцию; диагностика для такого места прямо об
этом говорит.

### 8.3 Контракт сигнатуры

```
func Name([ctx context.Context,] p1 T1, …, pn Tn) R
func Name([ctx context.Context,] p1 T1, …, pn Tn) (R, error)
```

- **H-8.3a** Параметры сопоставляются с параметрами JS по позиции. Вызов из
  JS с меньшим числом аргументов передаёт `undefined` для отсутствующих,
  поэтому соответствующий Go-параметр должен уметь его принять (`any`,
  указатель или `vela.Optional[T]`); иначе место вызова — ошибка сборки.
- **H-8.3b** Допустимые типы параметров и результатов (граничные типы):
  `string`, `bool`, `float64`, знаковые и беззнаковые целые типы (только для
  параметров; проверяемое преобразование, §8.4), `[]T`, `map[string]T`,
  структуры и указатели на структуры, удовлетворяющие T-5.1b, `time.Time`
  (для параметра — разбирается из ISO-строки), `any`, `vela.Optional[T]`.
- **H-8.3c** Необязательный первый параметр `context.Context` получает
  контекст, переданный рендереру. У рендереров появляется
  `RenderXContext(ctx, w, props, slots)`; существующие точки входа остаются и
  передают `context.Background()`. Так локаль, пользователь и данные запроса
  попадают в host-функции форматирования, не становясь пропами.
- **H-8.3d** Вариативные JS-функции привязываются к Go-функции с
  вариативным последним параметром.
- **H-8.3e** Компилятор проверяет каждое место вызова на соответствие
  сигнатуре через `go/types`. Если тип аргумента известен статически, код
  преобразования генерируется во время компиляции. Если нет (динамический
  уровень), сгенерированный код вызывает типизированный runtime-конвертер,
  который при несоответствии возвращает `*vela.RenderError` (`TypeError`);
  он никогда не паникует.

### 8.4 Правила преобразования

| Значение JS → параметр Go | Правило |
| --- | --- |
| `number` → `float64` | без изменений |
| `number` → целый тип | должно быть конечным, целым и в диапазоне; иначе `RangeError` |
| `string` → `time.Time` | разбор RFC 3339; ошибка разбора — `RangeError` |
| `null` → указатель / `any` / `Optional` | `nil` / `nil` / `Optional{Null: true}` |
| `undefined` → `any` / `Optional` | `vela.Undefined()` / `Optional{Absent: true}` |
| объект → структура | через JSON-представление (семантика `json.Unmarshal`, неизвестные поля игнорируются) |
| результат Go → JS | через JSON-представление (T-5.1) |

### 8.5 Поведенческие обязательства разработчика

Эти обязательства компилятор не может полностью доказать. Инструменты из §11
обнаруживают их нарушения.

- **H-8.5a Эквивалентность.** Для каждого входного значения, которое до неё
  доходит, host-функция должна возвращать то же значение, что и JS-функция в
  браузере. Клиент продолжает использовать JS-реализацию для последующих
  обновлений; расхождение проявляется как несоответствие при гидратации или
  как визуальный скачок после первого обновления.
- **H-8.5b Детерминизм.** При одинаковых аргументах и контексте host
  возвращает одинаковое значение. Данные запроса приходят из `ctx`, а не из
  изменяемых глобальных переменных.
- **H-8.5c Ошибки.** Host сообщает о сбое через результат `error`. Рендерер
  оборачивает его в `*vela.HostError{Site, JSName, Err}` и возвращает.
  Компилятор не перехватывает паники в коде разработчика.

### 8.6 Заготовки и неразрушающая генерация

- **H-8.6a** Для каждого места вызова со статусом `unsupported`, которое
  исправляется host-привязкой, `vela --ssr-scaffold-hosts` создаёт заготовку,
  только если целевого файла нет:
  `ssrhost/<зеркальный путь>/<name>_host.go` с директивой, сигнатурой,
  выведенной из мест вызова, и телом, возвращающим
  `vela.ErrHostNotImplemented`. Существующие файлы никогда не изменяются.
- **H-8.6b** Заготовка, которая всё ещё возвращает
  `vela.ErrHostNotImplemented`, роняет рендер с ошибкой и позицией, поэтому
  не может незаметно попасть в продакшен.

### 8.7 Host-значения, которые не являются функциями

Константы `const` уровня модуля, используемые кодом области (например,
таблица валют), транслируются, если их инициализатор допущен. Если нет,
разработчик привязывает Go-функцию без параметров; она вызывается один раз за
рендер, и результат кэшируется только в пределах этого рендера.

## 9. Клиентские границы

### 9.1 Граница в шаблоне

```vela
{#client}
  <Chart :data={stats} />
  <p>Сейчас: {new Date().toLocaleTimeString()}</p>
{:else}
  <div class="chart-skeleton"></div>
{/client}
```

- **T-9.1a Синтаксис.** `{#client}…{/client}` с необязательной веткой-заглушкой
  `{:else}`. Это структурный блок того же семейства, что и `{#if}`; он может
  стоять везде, где допустим структурный блок, включая `#if`, `#each`,
  `#key`, `#await`, слоты компонентов и содержимое другого компонента.
- **T-9.1b Заглушка необязательна.** Без `{:else}` (или с пустым `{:else}`)
  сервер рендерит пустой собственный диапазон маркеров. Компилятор никогда не
  придумывает содержимое заглушки сам.
- **T-9.1c Область.** Заглушка — код области и подчиняется всем правилам
  этого документа. Основная ветка и все выражения внутри неё исключены из
  области (T-2.2): они не порождают SSR-диагностик и Go-кода.
- **T-9.1d Момент монтирования.** После фиксации гидратации компонента-
  владельца основная ветка монтируется обычным CSR-путём в собственный
  диапазон, а узлы заглушки удаляются. Внутри структурного владельца
  (например, строки `#each`) каждый экземпляр владельца монтирует свою
  границу. Отложенные стратегии (когда браузер свободен, при появлении в
  области видимости) не входят в v1.
- **T-9.1e Жизненный цикл.** Граница принадлежит своему структурному
  владельцу: при уничтожении владельца смонтированное содержимое (или
  ожидающее монтирование) уничтожается вместе с ним. Откат транзакции
  гидратации владельца отменяет ожидающее монтирование.
- **T-9.1f CSR-сборки.** В сборке без `--ssr` блок `{#client}` сразу
  рендерит основную ветку и игнорирует `{:else}`.
- **T-9.1g Payload.** Из основной ветки ничего не сериализуется. Нужные ей
  значения клиент вычисляет после монтирования.

### 9.2 Компоненты только для клиента

```vela
<script context="client">
  export let data = [];
  // код только для браузера
</script>
```

- **T-9.2a** Компонент, чей скрипт объявлен с `context="client"`, работает
  только на клиенте. Компилятор не генерирует для него Go-рендерер.
- **T-9.2b** Каждое использование такого компонента понижается так, как если
  бы оно было обёрнуто в `{#client}<X … />{/client}` с пустой заглушкой.
  Родитель может задать заглушку, написав обёртку явно. Это явное объявление
  автора компонента, поэтому T-4.2 по-прежнему выполняется.
- **T-9.2c** Пропы, события, привязки и содержимое слотов, передаваемые
  такому компоненту, вычисляет только клиент; они исключены из области
  родителя.
- **T-9.2d** В CSR-сборках такой компонент ведёт себя как обычный.

### 9.3 Управление структурой

- **T-9.3** Значение, которое управляет структурой (T-4.3) и не может быть
  вычислено на сервере, нужно перенести внутрь блока `{#client}` вместе со
  структурой, которой оно управляет. Диагностика для такого места прямо об
  этом говорит.

## 10. Диагностики

### 10.1 Обязательное содержимое

Каждая SSR-диагностика включает:

1. код и позицию в исходнике наименьшего проблемного узла;
2. цепочку причин от корня области до этого узла, например
   `$derived "paras" → call "split" → regex literal argument`;
3. хотя бы одно конкретное исправление. Для host-исправления указываются
   точный путь host-файла, директива и Go-сигнатура, выведенная из мест
   вызова.

Пример:

```
src/blocks/BarChart.vela:12:9: [error] VELA-SSR-HOST-MISSING
  formatCurrency (src/lib/format.js:3) uses Intl.NumberFormat, which has no
  server-native translation.
  reason: template text → call formatCurrency → new Intl.NumberFormat
  fix: implement it in Go:
    ssrhost/src/lib/format/format_currency_host.go
      //vela:host formatCurrency
      func FormatCurrency(ctx context.Context, value float64) (string, error)
    or run: vela --ssr --ssr-scaffold-hosts
```

Тексты диагностик в выводе компилятора остаются на английском, как и
остальные сообщения Vela.

### 10.2 Коды

| Код | Значение |
| --- | --- |
| `VELA-SSR-EXPR` | Конструкция вне допущенного языка (§6, §7). |
| `VELA-SSR-HOST-MISSING` | Функции нужна host-реализация, а она не объявлена. |
| `VELA-SSR-HOST-SIG` | Сигнатура host не совпадает с местами вызова или использует не граничный тип. |
| `VELA-SSR-HOST-STALE` | Директива указывает на отсутствующий JS-символ, или символ привязан дважды. |
| `VELA-SSR-IMPURE` | Запись в области за пределами T-6.6b. |
| `VELA-SSR-NONDET` | Недетерминированный API вне позиций, разрешённых T-6.6c. |
| `VELA-SSR-HYDRATION` | Структура шаблона вне текущего lifecycle гидратации; сообщается отдельно от трансляции. |

### 10.3 Агрегация

- **D-10.3a** Сообщать обо всех ошибках области компонента за одну сборку, а
  не только о первой.
- **D-10.3b** Сообщать о функции один раз в месте её определения и затем
  перечислять места вызова. Не повторять ошибку для каждого места вызова.
- **D-10.3c** Ошибка дочернего компонента выводится один раз, у дочернего
  компонента. Родитель получает одну заметку со ссылкой на него, а не копию
  его ошибок.

### 10.4 Отчёт

`vela --ssr --ssr-report=<file.json>` записывает записи T-2.3 для всех
компонентов: исход, уровень, тип и host-привязку для каждого места и режим
артефакта для каждого компонента. CI использует этот отчёт для отслеживания
корпуса совместимости; переход места из `server-native` или `server-host` в
`unsupported` — регрессия.

## 11. Проверка

### 11.1 Каталог встроенных функций

- **V-11.1a** Допущенные встроенные функции перечислены в одной Go-таблице,
  которая является источником истины. У каждой записи: имя в JS и тип
  получателя, исход, Go-хелпер, поддерживаемые уровни, ID строк оракула и
  объявленные расхождения. `SSR_TRANSLATION_MATRIX.md` генерируется из этой
  таблицы. Пока таблицы нет (этап S5), матрица ведётся вручную, и каждое
  изменение транслятора обновляет её строки в том же коммите.
- **V-11.1b** Встроенная функция допускается только вместе со строками
  оракула и реализацией для динамического уровня (T-5.4a).

### 11.2 Оракулы и дифференциальное тестирование

- **V-11.2a** У каждого оператора и встроенной функции есть отслеживаемые
  строки оракула, которые вычисляются в Node и в сгенерированном Go на обоих
  уровнях. Существующий формат `testdata/ssr_*_oracle.json` расширяется, а не
  заменяется.
- **V-11.2b** Дифференциальный фаззинг: генератор создаёт случайные значения
  из области JSON-значений плюс `undefined` и случайные допущенные выражения
  над ними. Тест вычисляет их в Node и в сгенерированном Go и сравнивает
  результаты и виды ошибок. Любое расхождение становится фиксированной
  строкой оракула.
- **V-11.2c** Обязательные граничные строки для каждой числовой и строковой
  встроенной функции: `NaN`, `±Infinity`, `-0`, ничьи округления
  `0.5`/`2.5`/`-2.5`, целые больше 2^53, пустая строка, символы вне BMP,
  одиночные суррогаты, `null`, `undefined`, пустой массив, дыры в массиве.

### 11.3 Инструменты проверки эквивалентности host

- **V-11.3a Режим сборки.** У CLI есть явный режим сборки:
  `--mode=development|production`, по умолчанию `development`. Режим не
  зависит от `--minify`. Production-сборки не содержат кода проверки.
- **V-11.3b Проверка гидратации.** В dev-сборках гидратор вычисляет каждое
  принятое текстовое и атрибутное место через клиентский JS и сравнивает
  результат с серверным DOM. Сообщение о расхождении содержит позицию в
  исходнике, ID места, host-символ (если он есть) и оба значения:

  ```
  [vela] hydration mismatch at src/OrdersTable.vela:14:9 (site 7, host formatCurrency)
    server: "$1,234.5"   client: "$1,234.50"
  ```

  Структурные места (выбранная ветка `#if`, число строк `#each`, состояние
  `#await`) в v1 не сравниваются.
- **V-11.3c Политика проверки.** `--hydration-verify=repair|fail|off`; по
  умолчанию в development — `repair`.
  - `repair`: предупреждение в консоли, запись клиентского значения в DOM,
    гидратация продолжается. Для повседневной разработки.
  - `fail`: сообщение о расхождении, откат транзакции гидратации
    (существующий контракт отката) и ошибка с кодом
    `VELA-HYDRATION-MISMATCH`. Для CI и тестов; строгий браузерный раннер
    использует эту политику.
  - `off`: сравнения нет.

  Сочетание `--hydration-verify` с `--mode=production` — ошибка CLI.
- **V-11.3d Расхождение кодировки.** Значения, отличающиеся только заменой
  на U+FFFD по T-6.3b, считаются равными.
- **V-11.3e Host-фикстуры (необязательно).** Разработчик может добавить
  `ssrhost/<путь>/<name>_cases.json` со строками вход/выход. Компилятор
  генерирует из этого файла Go-тест и Node-тест, так что одни и те же строки
  проверяют и host-реализацию, и JS-реализацию.

## 12. Runtime (Go и JavaScript)

### 12.1 Модуль и версии

- **R-12.1a Вложенный модуль.** Go-runtime — вложенный Go-модуль в
  репозитории компилятора: каталог `ssr_runtime/` со своим `go.mod`. Имя
  пакета остаётся `ssr_runtime`. Сгенерированный код и документация
  импортируют его под принятым алиасом `vela`; поэтому примеры в этом
  документе пишут `vela.PublicError`.
- **R-12.1b Путь модуля.** Модуль runtime —
  `github.com/elauven/vela/ssr_runtime` (зафиксирован 2026-10-11). В
  компиляторе он встречается ровно в одном месте (константа
  `SSRRuntimeImportPath`) и может быть переопределён для проекта в
  `vela.ssr.json` (`"runtime": {"module": "…"}`) для форка.
- **R-12.1c Версии.** Релизы помечаются тегами `ssr_runtime/v0.x.y`. Пока
  версия `v0`, несовместимые изменения допускаются. Модуль компилятора не
  требует модуль runtime: его импортируют только тесты, через закоммиченный
  `go.work`, поэтому `go install` компилятора не нужна ни версия runtime, ни
  `replace`. Реализовано в задаче 049 (2026-10-09).
- **R-12.1d Проверка контракта.** Runtime экспортирует маркер контракта
  (сейчас `ContractV1`, `ssr_runtime/contract.go`; компилятор называет его в
  `SSRRuntimeContract`), и каждый сгенерированный файл ссылается на маркер,
  под который он сгенерирован (`var _ = vela.ContractV1`). Тогда
  несовпадение версий компилятора и runtime роняет `go build` с ошибкой
  неопределённого идентификатора, а не приводит к неправильному поведению во
  время выполнения. Маркер меняется, когда сгенерированный код начинает
  зависеть от нового или изменённого API runtime.

### 12.2 Поставка JavaScript-runtime

- **R-12.2a Источник истины.** JavaScript-runtime живёт в каталоге `runtime/`
  репозитория. Он заменяет прежний корневой `runtime.js` и его
  реэкспорт `runtime/runtime.js`; никакая другая копия не редактируется вручную.
  Компилятор встраивает runtime из `runtime/`. Runtime разделён на модули по
  областям: ядро реактивности и планировщик, DOM, гидратация и
  dev-проверки.
- **R-12.2b Один экземпляр на страницу.** Все сгенерированные модули одной
  сборки обязаны импортировать один и тот же URL модуля runtime. Копия в
  каждом каталоге вывода недопустима: каждая копия загружается и выполняется
  отдельно, а копии ведут себя как один runtime, только пока всё общее
  состояние runtime хранится на `globalThis` (сейчас очередь батчинга и метка
  прокси используют `Symbol.for`). Один URL модуля делает гарантией саму
  идентичность модуля.
- **R-12.2c Варианты сборки.** `--mode=production` исключает модуль
  dev-проверок (V-11.3); сборки без `--ssr` исключают модуль гидратации.
- **R-12.2d Проверка контракта на клиенте.** Сгенерированные модули
  импортируют из runtime именованный экспорт контракта (например,
  `$$contractV3`). Тогда несовпадение версий падает уже при загрузке модуля
  с ошибкой отсутствующего экспорта — тот же принцип, что в R-12.1d.
- **R-12.2e Этап 1 (сейчас).** Компилятор записывает runtime один раз в
  корень клиентского вывода, а сгенерированные модули импортируют его по
  вычисленным относительным путям.
- **R-12.2f Этап 2 (до беты; переписано 2026-10-09).** Vela — компилятор:
  его вывод — обычные ES-модули для инструментов самого приложения
  (бандлер, import map, сервер), и он никогда не разрешает, не копирует, не
  хеширует и не собирает зависимости приложения. Импорты пакетов выводятся
  как написаны. Runtime дополнительно публикуется как npm-пакет
  `@govela/runtime`, генерируемый из `runtime/` в `packages/runtime` (тест на
  расхождение), с версией компилятора и экспортами `.`, `./blocks` и
  `./hydrate`; его проверку режима разработки сворачивает замена
  `process.env.NODE_ENV` в бандлере. `--runtime-import=relative|bare`
  выбирает форму импорта runtime: `relative` (по умолчанию) кладёт runtime
  рядом с выводом, как на этапе 1; `bare` импортирует пакет и ничего не
  кладёт, так что бандлер берёт один экземпляр runtime из `node_modules`
  (R-12.2b), а маркер контракта (R-12.2d) падает при сборке бандлером, если
  версии не совпадают. Манифест проекта перечисляет импорты пакетов каждого
  сгенерированного модуля. Прежний план — копия runtime в `ssr_runtime` с
  `AssetsHandler()` / `HeadTags()` — отменён: раздача и хеширование —
  задача приложения.
- **R-12.2g Этап 3 (публикация).** npm-пакет публикуется с каждым релизом
  компилятора вместе с Go-модулем runtime (R-12.1c).

### 12.3 Дополнения к API

Добавляются в Go-пакет runtime:

- `vela.Object` — объект с порядком вставки и порядком перечисления ключей,
  как в JS.
- `vela.Optional[T]` — тип параметра host, различающий отсутствие, `null` и
  значение.
- `vela.RenderError`, `vela.HostError`, `vela.ErrHostNotImplemented`.
- `vela.PublicError` и `vela.WithErrorObserver` (T-7.4h).
- `vela.Promise` — завершённое значение-промис для синхронной модели (T-7.4b).
- Хелперы динамического уровня для всех допущенных операторов и встроенных
  функций; они заменяют специализированные хелперы вроде `NumberMultiply`
  там, где те сейчас принимают `any`.
- Точки входа `RenderXContext` (H-8.3c).

## 13. Этапы поставки

Каждый этап заканчивается прогоном `go test ./...`, строгого браузерного
раннера и обновлением `--ssr-report` для `test_projects`.

1. **IR и область.** Серверный IR, анализ области (T-2), отчёт по местам
   (T-2.3, §10.4) и исключение обработчиков событий. Поведение совпадает с
   текущим транслятором; отчёт по корпусу становится метрикой прогресса.
2. **Динамический уровень и инициализация.** T-5.4 и T-6.6d: `$state(prop)`,
   цепочки `$derived`, вычисленные значения в payload, `*vela.Object`.
3. **Host-привязки.** §8 полностью, с заготовками, диагностиками (§10) и
   `RenderXContext`.
4. **Операторы и модули.** §7: хелперы из нескольких операторов, `try` /
   `catch` / `finally`, `async` / `await` с синхронной моделью и
   вычисляемые на сервере `{#await}` (§7.4), локальные модули `.js`.
5. **Каталог встроенных функций.** §11.1 в порядке частоты использования в
   корпусе: строки, массивы, `Math`, форматирование `Number`,
   `JSON.stringify`.
6. **Клиентские границы.** §9: `{#client}` и компоненты только для клиента.

Независимо от этапов и до беты нужны: режим сборки и проверка гидратации
(V-11.3a–d), вложенный модуль runtime с проверкой контракта (§12.1), этапы
1 и 2 поставки JavaScript-runtime (§12.2).

## 14. Заменённые предложения

- Встроенный в шаблон обход через Go `{expr | go("…")}` из раннего дизайна
  (Option C) отменён. Go-код живёт только в дереве host.
- JSON-манифест `hostFunctions` из раннего дизайна заменён директивами
  `//vela:host` в Go (H-8.2b). В `vela.ssr.json` остаются только пути уровня
  проекта.
- Ограничение «ровно один `return`» для локальных форматтеров становится
  оптимизацией (T-7.1a).
- `SSRTypeInt` как тип транслированных значений заменяется на `number` →
  `float64`. Целочисленные Go-типы остаются допустимыми для пропов
  разработчика и параметров host.
- Объектные литералы, понижаемые в `map[string]any`, заменяются на
  `*vela.Object` (T-5.1c).
- Строка таблицы возможностей раннего дизайна «Promise, async/await, timers,
  fetch — `client-deferred` по умолчанию» заменена §7.4: асинхронный код в
  области выполняется на сервере синхронно; таймеры и браузерный ввод-вывод
  никогда не транслируются нативно.
- «`{#await}` на сервере рендерит pending» заменено T-7.4f для операндов,
  вычисляемых на сервере. Строковые `AwaitSnapshot.Value` / `Error`
  становятся JSON-значениями.

## 15. Решения

Приняты 2026-10-03:

1. Порог мономорфизации — 4 варианта для беты (T-7.2a); будет пересмотрен по
   итогам тестирования беты.
2. `try` / `catch` / `finally` и `async` / `await` входят в v1 с синхронной
   моделью выполнения (T-6.5d, §7.4).
3. Клиентские границы — блок `{#client}…{:else}…{/client}`; заглушка
   необязательна; содержимое монтируется сразу после гидратации владельца;
   компонент целиком можно объявить клиентским (§9).
4. Явный режим `--mode=development|production`; проверка гидратации по
   умолчанию включена в development, с выбором политики `repair` / `fail`;
   структурные места в v1 не сравниваются (V-11.3a–d).
5. Go-runtime — вложенный модуль `ssr_runtime/` с именем пакета
   `ssr_runtime`, тегами `v0.x` и проверкой контракта при сборке; публичный
   путь модуля остаётся настраиваемым до выбора имени репозитория (§12.1).
6. JavaScript-runtime переносится в `runtime/` и поставляется в три этапа:
   сейчас — одна копия с относительными путями, до беты — голый спецификатор
   с import map и раздачей через Go, при публикации — npm-пакет (§12.2).

Открытых решений нет.
