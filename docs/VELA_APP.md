# Working with vela-app

`vela-app` is the command-line tool of Vela App ([APP.md](APP.md)). It
generates the app sources from the routes tree, runs the development loop,
and makes a production build that can be deployed as one directory. This
page covers installing it, creating a project, developing, building and
deploying. The rules it implements are in [APP.md](APP.md).

| Command | What it does |
| --- | --- |
| `vela-app gen` | Generates `src/_app/` and `internal/appgen/routes_gen.go` from `src/routes` and `server/routes` |
| `vela-app watch` | Runs `gen` again on every change of the routes, the mirrored Go tree and the matchers |
| `vela-app scaffold [route]` | Creates the missing `load.go` files, for one route or for all |
| `vela-app dev` | Development: the generator, `vela --watch`, the Go server restarted after each good build, and Vite |
| `vela-app build` | Production build: `gen`, `vela`, `vite build` and `go build` of the server into a directory to deploy |
| `vela-app version` | Prints the version |

`-C dir` before the command runs it in another directory:
`vela-app -C site build`.

## Install

`vela-app` is versioned with the app layer (`app/vX.Y.Z`), not with the
compiler. Use the same version for the Go module
`github.com/elauven/vela/app`, the npm package `@govela/app` and the
command. Each release states the minimum compiler and runtime it needs;
`0.1.2` needs `vela`, `ssr_runtime` and `@govela/runtime` `0.4.8` or later.

### With npm (recommended for projects that use Vite)

`@govela/app` contains the client router and the `vela-app` command. npm
installs the binary for your platform as an optional dependency
(`@govela/app-linux-x64`, `-linux-arm64`, `-darwin-x64`, `-darwin-arm64`,
`-win32-x64`):

```sh
npm install @govela/app @govela/runtime
npm install -D @govela/compiler @govela/unplugin vite
npx vela-app version
```

npm scripts find `vela-app` and `vela` in `node_modules/.bin`, so
`vela-app dev` and `vela-app build` use the compiler of the project. Do not
install with `--omit=optional` or `--no-optional`: that skips the binary.
`VELA_APP_BINARY` makes the launcher run another `vela-app` binary.

### With Go

```sh
go install github.com/elauven/vela/app/cmd/vela-app@latest
```

To pin the version in the project, add it as a tool of the module
(Go 1.24 and later) and run it with `go tool`:

```sh
go get -tool github.com/elauven/vela/app/cmd/vela-app@v0.1.2
go tool vela-app gen
```

### Prebuilt binaries

Every release `app/vX.Y.Z` on
[GitHub Releases](https://github.com/elauven/vela/releases) has
`vela-app-<os>-<arch>` for linux, darwin (amd64, arm64) and windows (amd64),
and `SHA256SUMS`:

```sh
curl -LO https://github.com/elauven/vela/releases/download/app%2Fv0.1.2/vela-app-linux-amd64
curl -LO https://github.com/elauven/vela/releases/download/app%2Fv0.1.2/SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
install -m 755 vela-app-linux-amd64 /usr/local/bin/vela-app
```

The compiler `vela` comes from its own release (`vX.Y.Z`) or from
`@govela/compiler`; `vela-app` runs `$VELA_BINARY`, else `vela` from `PATH`.

## A new project

A Vela App project is a Go module and an npm project in one directory:

```
site/
  go.mod                     module example.com/site
  package.json               npm scripts and the JavaScript dependencies
  vela.config.json           the compiler configuration, with "ssr": true
  vite.config.js             the client build
  cmd/server/main.go         your server: app.New and your own handlers
  src/routes/                the routes tree: Layout.vela, Page.vela, Error.vela
  server/routes/             the mirrored Go tree: load.go, actions.go
  src/_app/                  generated by vela-app (not committed)
  internal/appgen/           generated by vela-app (not committed)
  out/                       generated by vela (not committed)
  dist/                      generated by vite build (not committed)
  build/                     generated by vela-app build (not committed)
```

`examples/app` in the repository is a complete project with every feature.

### Configuration files

`go.mod` requires the app layer and the Go runtime:

```sh
go mod init example.com/site
go get github.com/elauven/vela/app@v0.1.2 github.com/elauven/vela/ssr_runtime@v0.4.8
```

`vela.config.json` compiles `src` with server rendering; `ssrModule` is the
import path of the generated renderers, `<module>/<out>/server`:

```json
{
  "project": "src",
  "out": "out",
  "ssr": true,
  "ssrModule": "example.com/site/out/server"
}
```

For a TypeScript project, `vela.app.json` says so, and `tsconfig.json`
extends the configuration `vela-app gen` writes, which maps `./$types` of
each route directory to the types generated from its Go loaders
([APP.md](APP.md), Route types):

```json
// vela.app.json
{ "typescript": true }
```

```json
// tsconfig.json
{ "extends": "./src/_app/tsconfig.json", "include": ["src"] }
```

Install `typescript` (5.8 or 6.x) and check with
`npx vela check --project src --types`; the route types need the app layer
of this release or later (`github.com/elauven/vela/app/typegen`).

`vite.config.js` builds the generated client entry with a manifest, which
the server reads:

```js
import vela from '@govela/unplugin/vite';

export default {
  plugins: [vela()],
  server: { origin: 'http://localhost:5173' },
  build: { manifest: true, rollupOptions: { input: 'src/_app/client.js' } },
};
```

`package.json`:

```json
{
  "private": true,
  "type": "module",
  "scripts": {
    "gen": "vela-app gen",
    "dev": "vela-app dev",
    "build": "vela-app build"
  },
  "dependencies": {
    "@govela/app": "0.1.2",
    "@govela/runtime": "0.4.8"
  },
  "devDependencies": {
    "@govela/compiler": "0.4.8",
    "@govela/unplugin": "0.4.8",
    "vite": "^8.3.5"
  }
}
```

`.gitignore`:

```
/src/_app/
/internal/appgen/
/out/
/dist/
/build/
/node_modules/
```

### The server

`cmd/server/main.go` is your program: the app is one `http.Handler` next to
your own handlers. `vela-app dev` and `vela-app build` expect the flags
below (`-addr`, `-dev`, `-dist`); keep them if you write your own server.

```go
package main

import (
	"flag"
	"fmt"
	"log"
	"net"
	"net/http"
	"os"
	"path/filepath"

	"example.com/site/internal/appgen"
	"github.com/elauven/vela/app"
	"github.com/elauven/vela/ssr_runtime/vite"
)

func main() {
	addr := flag.String("addr", "127.0.0.1:8080", "listen address")
	dev := flag.String("dev", "", "URL of the Vite dev server; serve dist/ when empty")
	dist := flag.String("dist", "dist", `directory of vite build; "none" serves pages without client`)
	flag.Parse()

	mux := http.NewServeMux()
	var assets *vite.Assets
	switch {
	case *dev != "":
		assets = vite.Dev(*dev)
	case *dist != "none":
		var err error
		if assets, err = vite.Load(filepath.Join(*dist, ".vite", "manifest.json"), "/"); err != nil {
			log.Fatal(err)
		}
		mux.Handle("/assets/", http.FileServer(http.Dir(*dist)))
	}
	handler, err := app.New(app.Config{
		Routes:   appgen.Routes(),
		Assets:   assets,
		Manifest: filepath.Join("out", "client", "vela.manifest.json"),
		Head:     app.Head{Title: "Site"},
		Dev:      *dev != "",
	})
	if err != nil {
		log.Fatal(err)
	}
	mux.Handle("/", handler)

	listener, err := net.Listen("tcp", *addr)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Fprintf(os.Stdout, "http://%s\n", listener.Addr())
	log.Fatal(http.Serve(listener, mux))
}
```

The paths `dist` and `out/client/vela.manifest.json` are relative to the
working directory. That is why `vela-app build` copies them into the build
directory, next to the binary, and why the server runs in that directory.

### The first route

`src/routes/Layout.vela` wraps every page, `src/routes/Page.vela` is `/`:

```vela
<!-- src/routes/Layout.vela -->
<script>
  export let data = null;
</script>

<template>
  <nav><a href="/">Home</a></nav>
  <main><slot /></main>
</template>
```

```vela
<!-- src/routes/Page.vela -->
<script>
  export let data = null;
</script>

<template>
  <h1>{data.greeting}</h1>
</template>
```

`npx vela-app scaffold` creates `server/routes/load.go` with a loader per
component, `Layout` and `Page`, returning `nil`. Fill in the ones that load
data; a loader may return any type that marshals to JSON:

```go
func Page(ctx context.Context, r *app.Request) (map[string]string, error) {
	r.Head().Title = "Home"
	return map[string]string{"greeting": "Hello"}, nil
}
```

Then:

```sh
npm install
npx vela-app gen && npx vela   # once, so that go mod tidy sees internal/appgen and out/server
go mod tidy
npm run dev
```

Routes, parameters, layouts, error pages, loaders and actions are described
in [APP.md](APP.md) and in the Vela App section of [GUIDE.md](GUIDE.md).

## Development

```sh
npm run dev                # vela-app dev
```

`vela-app dev` runs, each with its prefix on the output:

| Prefix | Process |
| --- | --- |
| `[gen]` | the generator, in process: regenerates on every change of the routes and the Go tree |
| `[vela]` | `vela --watch` (`$VELA_BINARY` or `vela`) |
| `[server]` | `go run ./cmd/server -dev http://localhost:5173`, started after the first good build and restarted after every good build and every change of a Go file |
| `[vite]` | `npx vite`, the dev server of the client modules |
| `[dev]` | the loop itself: restarts and exits |

Open the server's URL (`http://127.0.0.1:8080` by default), not Vite's.
Ctrl-C stops everything; when `vela` or Vite exits, `dev` stops too; when the
server exits (a compile error in Go), the next change starts it again.

Flags replace the commands; a command is split at spaces, and `""` runs
none:

```sh
vela-app dev -server "go run ./cmd/server -addr :3000 -dev http://localhost:5173"
vela-app dev -vite ""                       # no Vite: pages are served without client
vela-app dev -vela "npx vela --watch"
```

## Production build

```sh
npm run build              # vela-app build
```

`vela-app build`:

1. generates the app sources (`gen`), and stops on `VELA-APP-*` errors;
2. compiles the components with `vela` (client modules and Go renderers);
3. builds the client with `npx vite build` into `dist/`;
4. builds the server with `go build -trimpath ./cmd/server`;
5. writes the build directory, `build/` by default:

```
build/
  server                         the server binary (server.exe on Windows)
  dist/                          the client: assets/ and .vite/manifest.json
  out/client/vela.manifest.json  the root modes of vela (static sections, R-9)
  .vela-app-build                the marker of a directory vela-app build owns
```

| Flag | Default | Meaning |
| --- | --- | --- |
| `-o dir` | `build` | the build directory. It is replaced on each build, but only when it is empty or has `.vela-app-build`; any other directory is refused |
| `-server pkg` | `./cmd/server` | the Go package of the server; `""` builds no binary |
| `-vite cmd` | `npx vite build` | the client build; `""` runs none |
| `-vela cmd` | `$VELA_BINARY` or `vela` | the compiler |

`go build` takes its usual environment, so cross-compilation works the same
way: `GOOS=linux GOARCH=arm64 CGO_ENABLED=0 vela-app build` builds a Linux
arm64 binary on any machine (the name gets `.exe` for `GOOS=windows`).

The build id of the documents is a hash of the Vite manifest, so every
client build gets a new one. Pages that stay open across a deploy load the
new build on their next navigation ([APP.md](APP.md#deploys)).

## Deploy

The build directory is all the server needs at run time: the binary has the
Go renderers, the loaders and the app layer compiled in, and reads `dist/`
and the vela manifest from its working directory. Node and Go are needed
only for the build.

```sh
rsync -a --delete build/ server:/srv/site/
ssh server 'cd /srv/site && ./server -addr :8080'
```

The server prints its URL on the first line and logs to the standard error.
Run it in the build directory, or with absolute `-dist` and manifest paths.
Listen on `127.0.0.1` behind a reverse proxy (nginx, Caddy), or on `:8080`
in a container.

### systemd

```ini
# /etc/systemd/system/site.service
[Unit]
Description=Site
After=network.target

[Service]
WorkingDirectory=/srv/site
ExecStart=/srv/site/server -addr 127.0.0.1:8080
Restart=on-failure
User=site

[Install]
WantedBy=multi-user.target
```

A deploy copies the new build directory and restarts the service:
`systemctl restart site`.

### Docker

The build stage has Go and Node; the final image has only the build
directory. With `CGO_ENABLED=0` the binary is static and runs in a
distroless image.

```dockerfile
# Dockerfile
FROM node:24-bookworm AS build
COPY --from=golang:1.25-bookworm /usr/local/go /usr/local/go
ENV PATH=/usr/local/go/bin:$PATH CGO_ENABLED=0
WORKDIR /src
COPY package.json package-lock.json ./
RUN npm ci
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN npx vela-app build -o /site

FROM gcr.io/distroless/static-debian12
COPY --from=build /site /site
WORKDIR /site
EXPOSE 8080
ENTRYPOINT ["/site/server", "-addr", ":8080"]
```

```
# .dockerignore
node_modules
src/_app
internal/appgen
out
dist
build
```

```sh
docker build -t site .
docker run --rm -p 8080:8080 site
```

### Continuous integration

```yaml
# .github/workflows/build.yml
name: Build
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-go@v6
        with: { go-version: '1.25' }
      - uses: actions/setup-node@v5
        with: { node-version: '24', cache: npm }
      - run: npm ci
      - run: npx vela-app build
        env: { CGO_ENABLED: '0' }
      - uses: actions/upload-artifact@v4
        with: { name: site, path: build/, include-hidden-files: true }
```

## Troubleshooting

| Symptom | Cause and fix |
| --- | --- |
| `vela-app: the package @govela/app-<platform> is not installed` | npm skipped optional dependencies. Reinstall without `--omit=optional`, or set `VELA_APP_BINARY` |
| `vela-app: no prebuilt binary for <platform>` | Build it with `go install github.com/elauven/vela/app/cmd/vela-app@vX.Y.Z` and set `VELA_APP_BINARY` |
| `vela: executable file not found` | `vela-app` runs `$VELA_BINARY` or `vela` from `PATH`. Run it through npm (`npx vela-app`, npm scripts) with `@govela/compiler` installed, or set `VELA_BINARY` |
| `VELA-APP-CONFIG` and other `VELA-APP-*` errors | The generator's diagnostics ([APP.md](APP.md#diagnostics)); nothing is written until they are fixed |
| `go: … internal/appgen` or `… out/server/… cannot find module providing package` | The generated packages are missing: run `vela-app gen` and `vela` before `go mod tidy` or `go build` (`vela-app build` and `dev` do it) |
| `the output directory … was not written by vela-app build` | `-o` names a directory with files that `vela-app build` did not write. Remove it or choose another |
| Pages are served but nothing is interactive | The server runs without `dist/` (`-dist none`) or without Vite in development; check the `[vite]` output and the `/assets/` handler |
| An open page reloads after a deploy | Expected: the build id changed, and the router loads the new document ([APP.md](APP.md#deploys)) |
