# Контракт блочного runtime и универсальной гидратации

Статус: принятое направление, 2026-10-04. Владелец: задача 007; заменяет
подход к реализации задачи 029 и часть контракта артефактов задачи 027 (§11).

Это русская версия `HYDRATION_ARCHITECTURE.md`. Идентификаторы правил
совпадают. При расхождении текстов нормативной считается английская версия;
изменения вносятся в обе версии одновременно.

Документ задаёт нормативный контракт того, как Vela строит, обновляет и
«усыновляет» DOM-структуру в браузере. Он заменяет рецепты гидратации под
конкретные формы шаблона одним механизмом, который работает для любой
поддерживаемой структуры шаблона на любой глубине вложенности. Трансляция
выражений и host-реализации описаны в `SSR_TRANSLATION_CONTRACT.md`; этот
документ их не меняет.

Идентификаторы правил: `U-` принципы, `F-` фрагменты, `B-` блоки, `C-` курсор,
`M-` разметка, `S-` поток payload, `X-` расхождения и откат, `A-` артефакты и
API, `Q-` проверка, `G-` миграция.

## 1. Принципы

- **U-1.1 Один путь кода.** Монтирование в CSR и гидратация выполняют один и
  тот же сгенерированный код. Гидратация — это другой DOM-курсор, а не другой
  генератор.
- **U-1.2 Композиция, а не перечисление.** Структура поддерживается для
  гидратации тогда и только тогда, когда она поддерживается в CSR. Ни одно
  правило, предикат или ветка генератора не может зависеть от того, какой тип
  блока внутри какого находится.
- **U-1.3 Общие блоки в runtime.** Структурное поведение (`#if`, `#each`,
  `#key`, `#await`, компоненты, слоты, `{#client}`) реализуется один раз в
  runtime. Компилятор генерирует только фрагменты и код обновления с учётом
  зависимостей.
- **U-1.4 Компиляторная реактивность остаётся.** Сеттеры, флаги изменений и
  flush компонента сохраняют текущее устройство. Меняется только структурный
  слой.
- **U-1.5 Меньше вывода.** Сгенерированный код не должен содержать копий
  структурных алгоритмов (сверка списков, переключение веток, очистка) для
  каждого места в шаблоне.

### 1.1 Почему текущая модель не масштабируется

Сейчас каждый структурный блок генерируется прямо в теле компонента как
конечный автомат (`$$chain_*`, `$$each_*`). Состояние вложенного блока
поднято на уровень компонента (`$$n7_a`, `$$n7_km`, `$$n7_bs`), а внешний
блок вручную создаёт и уничтожает вложенный. Каждая пара «X внутри Y» — это
связка, которую пишет генератор, и гидратации пришлось повторять эту связку
для каждой пары: около 85 функций `buildHydration*` в `astgen.go`, предикаты
форм в `ssr_capability.go` и `ssr_nested_keyed_await_adoption.go`. Число пар
растёт комбинаторно с глубиной вложенности.

### 1.2 Термины

| Термин | Значение |
| --- | --- |
| Фрагмент | Сгенерированная функция, которая строит тело компонента, ветки, строки, слота или границы через курсор. |
| Блок | Объект runtime, реализующий структурную конструкцию (§3). |
| Владелец | Блок или экземпляр компонента, который освобождает ресурс при своём уничтожении. |
| Диапазон | DOM-узлы, которые занимает блок, ограниченные начальным и конечным комментарием. |
| Курсор | Объект, который выдаёт фрагментам DOM-узлы: созданные (CSR) или усыновлённые (гидратация) (§4). |
| Корень | Один вызов `hydrate()` или `mount()` и дерево под ним. |
| Поток | Упорядоченный payload одного корня (§6). |

## 2. Фрагменты

Фрагмент — единственный вид структурного кода, который генерирует компилятор.

```js
// {#each items as item (item.id)} <li @click={() => pick(item)}>{item.name}</li> {/each}
function row(c, s) {                     // c: курсор, s: лексическая область строки
  const li = c.element('li');
  c.listen(li, 'click', () => pick(s.item));
  c.enter(li);
  const t = c.text(`${s.item.name}`);
  c.exit();
  return {
    p(dirty) { if (dirty & ITEM) t.data = `${s.item.name}`; },
  };
}
```

- **F-2.1 Только через курсор.** При монтировании фрагмент получает каждый
  DOM-узел, значение атрибута, обработчик, привязку и дочерний блок через
  курсор. Он никогда напрямую не вызывает `document.createElement`,
  `appendChild`, `innerHTML` или `addEventListener`.
- **F-2.2 Начальные значения через курсор.** Начальные значения текста,
  атрибутов, свойств, классов и стилей передаются курсору, а не
  присваиваются напрямую. В режиме создания курсор их записывает; в режиме
  гидратации он принимает серверное значение и в development проверяет его
  (§7.2).
- **F-2.3 Детерминированная последовательность.** При одних и тех же входных
  данных фрагмент выполняет одни и те же вызовы курсора в порядке документа.
  Порядок берётся из общего render plan, по которому работает и
  Go-рендерер.
- **F-2.4 Область видимости.** Лексические привязки (элемент и индекс
  `#each`, значение или ошибка `#await`) передаются в объекте области
  видимости. Когда блок переиспользует фрагмент с новыми значениями
  (обновлённая строка, завершённый `then`), он обновляет область видимости и
  вызывает `p`.
- **F-2.5 Объект обновления.** Фрагмент возвращает `{ p(dirty) }`. `p`
  применяет изменения, отобранные маской изменений компонента, и передаёт её
  дочерним блокам, созданным этим фрагментом. Фрагмент, которому нечего
  обновлять, может вернуть пустой объект.
- **F-2.6 Никакой структурной связки.** Фрагмент никогда не обращается к
  внутренностям другого фрагмента или блока. Он хранит только созданные им
  объекты.

## 3. Блоки

### 3.1 Протокол

Каждый блок реализует:

```ts
interface Block {
  p(dirty: number): void      // обновление после flush компонента
  move(before: Node): void    // перемещение всего диапазона (keyed #each)
  destroy(): void             // освободить ресурсы и удалить диапазон
  abandon(): void             // освободить ресурсы, DOM не трогать
}
```

Блок создаётся через `c.block(kind, …)` и сразу монтируется через
переданный курсор.

- **B-3.1 Диапазон.** Блок владеет диапазоном между начальным и конечным
  комментарием. В режиме создания курсор создаёт оба комментария; в режиме
  гидратации он принимает серверные маркеры (§5) как комментарии диапазона.
- **B-3.2 Владение.** Блок, обработчик, привязка, дочерний компонент или
  отложенная задача, созданные при монтировании фрагмента, регистрируются у
  текущего владельца. Владельцы образуют дерево, повторяющее структуру
  шаблона.
- **B-3.3 Уничтожение.** `destroy()` освобождает ресурсы в порядке, обратном
  регистрации, затем удаляет диапазон блока. Потомки внутри удаляемого
  диапазона освобождают свои ресурсы, но не удаляют DOM по отдельности.
- **B-3.4 Отказ.** `abandon()` освобождает ресурсы в порядке, обратном
  регистрации, и делает недействительными ожидающие колбэки и отложенную
  работу, но никогда не меняет DOM. Это примитив отката (§7.3).
- **B-3.5 Поздняя работа.** Колбэки, запланированные уничтоженным или
  отказавшимся блоком (завершение промиса, отложенное монтирование, работа
  flush), ничего не делают.
- **B-3.6 Обновления после гидратации.** После фиксации корня любое
  монтирование, вызванное обновлением (новая ветка, новая строка,
  пересоздание поддерева `#key`), использует курсор создания, привязанный к
  диапазону блока.

### 3.2 Каталог блоков

| Блок | Создаётся из | Поведение |
| --- | --- | --- |
| `$$if(select, branches)` | `{#if}` / `{:else if}` / `{:else}` | `select()` возвращает индекс активной ветки или `-1`. При смене текущая ветка уничтожается и монтируется новая; при том же индексе вызывается `p` ветки. |
| `$$each(collection, key, row, fallback)` | `{#each}` с необязательным ключом и `{:else}` | С ключом: сохраняет, перемещает, создаёт и удаляет строки по ключу; сохраняет фокус, как текущий CSR. Без ключа: обновляет строки на месте по индексу. Каждая строка — блок со своим диапазоном. `fallback` монтируется, когда коллекция пуста. |
| `$$key(value, body)` | `{#key}` | Пересоздаёт тело при смене значения, с текущей семантикой CSR. |
| `$$await(operand, pending, then, catch)` | `{#await}` и его сокращённые формы | Следит за текущим операндом; завершение устаревшего операнда игнорируется. Гидратация — по §6.4. |
| `$$component(factory, props, slots, events, bindings)` | тег дочернего компонента | Создаёт дочерний экземпляр со своим владельцем. Обновления родителя передаются через `set` дочернего компонента. События компонента и `bind:` к пропу `$bindable` сохраняют текущую семантику. |
| `$$slot(name, fallback)` | `<slot>` в дочернем компоненте | Монтирует фрагмент слота, переданный родителем, или `fallback`, если слот не передан. |
| `$$client(main, fallback)` | `{#client}` и компоненты только для клиента | Контракт `SSR_TRANSLATION_CONTRACT.md` §9. В режиме гидратации принимает диапазон заглушки и монтирует `main` курсором создания после фиксации корня. В CSR монтирует `main` сразу. |

- **B-3.7 Владение слотами.** Фрагмент слота определяется родителем и
  монтируется внутри дочернего компонента. Им владеет блок `$$slot`
  дочернего компонента, который его уничтожает, а обновления родителя
  фрагмент получает через подписку, которую блок `$$slot` регистрирует у
  экземпляра родителя и снимает при уничтожении.
- **B-3.8 Несколько корней.** В первой поставке компоненты сохраняют текущую
  форму DOM в CSR, включая обёртку `display: contents` для шаблонов с
  несколькими корнями. Убирать ли обёртку — открытый вопрос (§12).

### 3.3 Форма сгенерированного компонента

- **B-3.9** Модуль компонента экспортирует публичную фабрику с текущей
  сигнатурой (`Component(target, props, slots)`, возвращающую `{ el, set,
  destroy }`) и внутреннюю точку входа для `$$component` и `hydrate()`,
  которая монтирует корневой фрагмент компонента через переданный курсор.
- **B-3.10** Возможности уровня элемента — это вызовы курсора, а не блоки:
  динамические атрибуты, `class:`, `style:`, DOM-события, `bind:value` /
  `bind:checked` / `bind:this` и привязки `<select>`, включая
  `<select multiple>`.

## 4. Курсор

### 4.1 API

Имена ориентировочные; семантика нормативна.

| Вызов | Режим создания | Режим гидратации |
| --- | --- | --- |
| `element(tag)` | создать элемент и вставить в текущую позицию | взять следующий узел; это должен быть элемент с этим тегом |
| `text(value)` | создать текстовый узел со значением `value` | взять следующий узел; это должен быть текстовый узел (см. C-4.3) |
| `static(id)` | клонировать статическое поддерево из шаблона уровня модуля | перешагнуть известное число узлов верхнего уровня этого поддерева |
| `enter(el)` / `exit()` | войти в дочерние узлы элемента / выйти | то же; при `exit` у элемента не должно остаться непрочитанных дочерних узлов |
| `attr`, `prop`, `cls`, `style` | записать начальное значение | не записывать; в development — проверить (§7.2) |
| `listen(el, event, handler)` | добавить обработчик, зарегистрировать у владельца | то же |
| `bind(el, kind, read, write)` | записать значение состояния в элемент формы | принять живое значение элемента (C-4.5) |
| `block(kind, …)` | создать комментарии диапазона и смонтировать блок | принять маркеры диапазона и смонтировать блок |

### 4.2 Правила

- **C-4.1 Две реализации, один интерфейс.** Курсоры создания и гидратации
  взаимозаменяемы для любого фрагмента. Курсор гидратации находится в модуле
  гидратации runtime (R-12.2c); сборки только для CSR его не содержат.
- **C-4.2 Строгий порядок.** Курсор гидратации читает серверный DOM строго в
  порядке документа. Любой неожиданный узел — расхождение (§7).
- **C-4.3 Текстовые участки.** На этапе компиляции каждый максимальный
  участок соседнего статического и динамического текста внутри одного
  родителя становится одним текстовым узлом, значение которого — шаблон (как
  уже делает текущий CSR с `` `${name} ` ``). Участки всегда разделены
  элементами или маркерами блоков, поэтому HTML-парсер никогда их не
  склеивает. Участка с пустым значением в разобранном HTML нет; тогда курсор
  гидратации вставляет пустой текстовый узел, и это не считается
  расхождением.
- **C-4.4 Переключение режима.** Корень использует курсор гидратации только
  до фиксации. После неё любое монтирование использует курсоры создания
  (B-3.6).
- **C-4.5 Элементы форм.** Гидратация `bind:value` / `bind:checked` читает
  живое значение DOM. Если пользователь изменил элемент до гидратации, живое
  значение записывается в состояние через обычный сеттер. Это сохраняет
  существующий контракт из `SSR.md`. `bind:this` присваивается после
  усыновления элемента и очищается при уничтожении.

## 5. Протокол разметки

Go-рендерер пишет HTML по тому же render plan, что и фрагменты, поэтому
последовательность узлов серверного HTML совпадает с последовательностью
вызовов курсора.

### 5.1 Грамматика

```
range      = "<!--[" state "-->" content "<!--]-->"
state      = ""            ; #each, #key, компонент, слот, строка
           | branch        ; #if: индекс активной ветки, десятичный; "x", если ветки нет
           | "e"           ; #each: отрендерена ветка {:else}
           | "p" | "t" | "c"   ; #await: pending / then / catch
           | "f"           ; $$client: отрендерена заглушка
```

Пример для шаблона из §2 внутри `{#if open}<ul>…</ul>{/if}`:

```html
<!--[0--><ul><!--[--><!--[--><li>Apple</li><!--]--><!--[--><li>Pear</li><!--]--><!--]--></ul><!--]-->
```

- **M-5.1 Только блоки.** Маркеры стоят только на границах блоков и строк.
  У элементов нет маркеров и идентификаторов экземпляров; они находятся по
  позиции.
- **M-5.2 Строки.** Каждая строка `#each` — отдельный диапазон, потому что у
  строки может быть несколько узлов верхнего уровня.
- **M-5.3 Никаких данных в маркерах.** Маркеры содержат только токен
  состояния. Ключи, значения и идентификаторы никогда не пишутся в маркеры.
- **M-5.4 Зарезервированные комментарии.** Комментарии, текст которых
  начинается с `[` или `]`, зарезервированы для маркеров. HTML-комментарии
  автора в шаблонах не выводятся ни в CSR, ни в SSR.
- **M-5.5 Текстовые участки.** Комментарии-разделители не используются;
  C-4.3 делает их ненужными.
- **M-5.6 Границы корня.** Корень рендерится как один диапазон, за которым
  сразу следует его скрипт payload (§6).

### 5.2 Стабильность разбора

Браузер должен разобрать серверный HTML ровно в ту последовательность узлов,
которую ожидает курсор. Компилятор гарантирует это на этапе компиляции.

- **M-5.7 Нормализация.** Конструкции, которые парсер меняет предсказуемо,
  нормализуются в обоих выводах: для строк таблицы, записанных прямо в
  `<table>`, явно вставляется `<tbody>`. Ведущий перевод строки, который
  парсер отбрасывает после `<pre>` и `<textarea>`, компенсируется в выводе
  Go.
- **M-5.8 Отклонение.** Конструкции, которые парсер переставляет, — ошибки
  компиляции с позицией и способом исправления (`VELA-HTML-NESTING`):
  - текст или блок прямо внутри `<table>`, `<thead>`, `<tbody>`, `<tfoot>`
    или `<tr>`, где парсер вынес бы его за пределы таблицы (foster
    parenting);
  - блочные элементы внутри `<p>`;
  - `<a>` внутри `<a>`, `<form>` внутри `<form>`, `<button>` внутри
    `<button>`;
  - элементы внутри `<option>`, дочерние узлы у void-элементов.
- **M-5.9 Элементы только с текстом.** Внутри `<textarea>`, `<title>`,
  `<script>` и `<style>` разрешён только один текстовый участок и никаких
  блоков; маркеров там быть не может. Содержимое `<textarea>`
  обрабатывается как значение формы (C-4.5).
- **M-5.10 Пробелы.** Обработка пробелов решается один раз, в render plan.
  Вывод Go и фрагменты используют уже решённые текстовые участки и никогда
  не обрезают и не схлопывают пробелы самостоятельно.

## 6. Поток payload

### 6.1 Формат

Один скрипт на интерактивный корень, сразу после диапазона корня:

```html
<script type="application/json" data-vela-root>
{"v":3,
 "props":{"title":"Team","users":[{"id":1,"name":"Ann"},{"id":2,"name":"Bob"}]},
 "entries":[
   ["s","Page",{"stats":{"active":2}}],
   ["a","Page#3",{"state":"t","value":{"total":2}}]
 ]}
</script>
```

Здесь у `Page` есть `let stats = $state(summarize(users))`, его значение
передаётся в payload; `let open = $state(true)` в `Page` и литеральное
состояние `Header` и `UserCard` клиент вычисляет сам (S-6.8a), поэтому
эти компоненты записей не пишут.

- **S-6.1 Один поток на корень.** Никаких скриптов на каждый компонент и
  идентификаторов экземпляров.
- **S-6.2 Пропы корня.** `props` содержит объявленные пропы корневого
  компонента после применения значений по умолчанию (существующие правила
  allow-list и сериализации, включая отдельное представление `undefined`).
- **S-6.3 Пропы дочерних компонентов не сериализуются.** Клиент вычисляет их,
  выполняя код родителя.
- **S-6.4 Записи.** В порядке рендера:
  - `["s", component, state]` — пишется, когда экземпляр компонента начинает
    рендериться: начальные значения его `$state` и `$state.deep` без
    воспроизводимого инициализатора (S-6.8a). Компонент без таких привязок
    записи не пишет, а его клиентский код её не читает; какие компоненты
    пишут запись, решается при компиляции из одного исходника, поэтому
    сервер и клиент согласованы (версия payload 3, задача 059). Пропсов
    `$bindable` в записи нет: клиент берёт их из пропсов (S-6.2, S-6.3).
  - `["a", site, snapshot]` — пишется, когда рендерится `{#await}`,
    вычисленный на сервере (T-7.4f). `site` — идентификатор места `await`,
    назначенный при компиляции.
- **S-6.5 Ничего для клиентского кода.** Основная ветка `{#client}` и
  компоненты только для клиента записей не создают.
- **S-6.6 Кодирование.** Значения следуют правилу JSON-представления
  (T-5.1). Содержимое скрипта экранируется так, чтобы оно не могло закрыть
  элемент script или открыть комментарий (экранируются `<`, `>`, `&`,
  U+2028, U+2029).

### 6.2 Чтение

- **S-6.7 Порядок, а не идентификаторы.** Клиент читает записи в том
  порядке, в каком курсор доходит до соответствующего компонента или блока
  `await`. Имя компонента или место в записи должны совпадать с ожидаемыми
  клиентом; иначе это расхождение.
- **S-6.8 Восстановленное состояние.** В режиме гидратации компонент берёт
  начальные значения `$state` из своей записи, а выражения-инициализаторы
  `$state` **не вычисляются**. Именно это предотвращает повторную загрузку
  данных и повтор на клиенте работы, которую на сервере выполнил host.
  Значения `$derived` и значения пропов по умолчанию вычисляются обычным
  образом.
- **S-6.8a Воспроизводимые инициализаторы.** Инициализатор, который клиент
  вычисляет сам, бесплатно и с тем же результатом, что сервер, вычисляется
  на клиенте и при гидратации, а его значение не пишется: дерево литералов
  (числа, строки, логические значения, `null`, `undefined`, массивы и
  простые объекты из них) или ссылка на проп и его поля (`columns`,
  `issue.title`). Между инициализатором и рендером на сервере состояние не
  меняется (обработчики, эффекты и хуки жизненного цикла там не
  выполняются), а пропсы доходят до клиента (S-6.2, S-6.3), поэтому значение
  на клиенте равно серверному. Вызовы, другие привязки и любые другие
  выражения по-прежнему передают значение в payload.
- **S-6.9 Удаление.** Скрипт payload удаляется после фиксации корня.

### 6.3 Списки с ключами

- **S-6.10** При гидратации `$$each` с ключом вычисляет ключи по
  восстановленной коллекции и усыновляет диапазоны строк по порядку. Число
  строк, отличное от длины коллекции, — расхождение. Повторяющиеся ключи
  ведут себя как в CSR.

### 6.4 Блоки await

- **S-6.11** При гидратации `$$await` читает свою запись `a`. Для `t` и `c`
  он усыновляет завершённую ветку с сериализованным значением или ошибкой и
  **не** вычисляет операнд. Операнд вычисляется заново только при изменении
  его зависимостей. Для `p` (рендерится, только если вызывающий код передал
  snapshot pending через `RenderOptions.Await`) он усыновляет ветку pending
  и вычисляет операнд после фиксации корня.

## 7. Расхождения, проверка и откат

### 7.1 Обнаружение

- **X-7.1** Курсор гидратации без дополнительных затрат проверяет: вид узла
  и тег, грамматику маркеров, индекс ветки `#if` против `select()`, число
  строк `#each`, состояние `#await` против записи, непрочитанные дочерние
  узлы при `exit`, вид и имя каждой записи потока.

### 7.2 Проверка значений

- **X-7.2** В development-сборках курсор дополнительно сравнивает начальные
  значения текста, атрибутов, свойств, классов и стилей, вычисленные
  клиентом, с усыновлёнными серверными значениями (V-11.3b).
  Production-сборки не содержат кода проверки значений.

### 7.3 Политики

| Ситуация | `repair` (по умолчанию в development) | `fail` (CI, тесты) | Production |
| --- | --- | --- | --- |
| Структурное расхождение | Ближайший объемлющий блок отказывается от серверного диапазона и перемонтируется курсором создания; предупреждение в консоли с позицией в исходнике. | Отказ от всего корня (B-3.4) и ошибка `VELA-HYDRATION-MISMATCH`. | Как `repair`, с одним `console.error` с кодом, без позиции в исходнике. |
| Расхождение значения | Записать клиентское значение; предупреждение в консоли. | Как выше. | Не проверяется. |

- **X-7.3 Расхождение в корне.** Расхождение на уровне диапазона самого
  корня перемонтирует весь корень. Это единственный случай, когда гидратация
  очищает контейнер.
- **X-7.4 Откат.** `fail` и любая ошибка, выброшенная во время гидратации,
  вызывают `abandon()` по дереву владельцев корня. Серверный DOM и payload
  остаются для исправленной повторной попытки. Независимо гидратированные
  корни не затрагиваются. Повторная попытка создаёт ровно один живой
  экземпляр. Так контракт отката задачи 027 выполняется в общем виде.
- **X-7.5 Хук отчётов.** `hydrate()` принимает опцию `onMismatch(report)`,
  которая получает каждое расхождение в любом режиме.

## 8. Корни, артефакты и API

### 8.1 Режимы корня

- **A-8.1 Два режима, на уровне корня.** Компонент, используемый как
  корень, рендерится в одном из двух режимов:
  - `interactive`: маркеры, поток payload и клиентский модуль;
  - `static`: обычный HTML без маркеров и payload, без JavaScript.
- **A-8.2 Определение static.** Компонент является `static` как корень, если
  во всём его дереве компонентов нет DOM-событий, директив `bind:` (включая
  `bind:this`), `$effect`, хуков жизненного цикла, блоков `{#client}` и
  компонентов только для клиента. Без них после рендера ничего не может
  измениться. `{#await}` с операндами, вычисляемыми на сервере, допускается.
- **A-8.3 Статический рендер интерактивных компонентов.** Каждый
  сгенерированный рендерер также предоставляет статический вариант, который
  пишет обычный HTML без маркеров и payload даже для компонента
  `interactive`. Сценарии: e-mail, фиды, заранее отрендеренные фрагменты.
- **A-8.4 Никаких режимов на уровне компонента.** Режимы артефактов
  `executable`, `static-only` и `client-boundary` на уровне компонента
  удаляются. Каждый компонент, который компилируется для CSR,
  гидратируется — с учётом исходов трансляции из
  `SSR_TRANSLATION_CONTRACT.md`.

### 8.2 Go API

```go
func RenderPage(w io.Writer, props PageProps, slots PageSlots) error
func RenderPageContext(ctx context.Context, w io.Writer, props PageProps, slots PageSlots) error
func RenderPageStatic(ctx context.Context, w io.Writer, props PageProps, slots PageSlots) error
func RenderPageWithOptions(ctx context.Context, w io.Writer, props PageProps, slots PageSlots, options PageRenderOptions) error
```

- **A-8.5** `RenderX` / `RenderXContext` пишут корень в его режиме (A-8.1).
  `RenderXStatic` реализует A-8.3. `RenderXWithOptions` сохраняет
  переопределения `Await` (T-7.4f) с ключом — идентификатором места `await`
  корневого компонента.
- **A-8.6** API с идентификаторами экземпляров (`RenderXAt`, `XAt`, параметр
  `instanceID`) удаляются; экземпляры не идентифицируются ни в разметке, ни
  в payload.

### 8.3 Клиентский API и выходные файлы

```js
import { hydrate, mount } from 'vela/runtime';
import Page from './Page.js';

hydrate(Page, document.getElementById('app'), { onMismatch: report => … });
```

- **A-8.7** `hydrate(Component, container, options)` ожидает внутри
  `container` ровно один диапазон корня и его скрипт payload. Несколько
  корней на странице используют несколько контейнеров.
- **A-8.8** Каждый компонент компилируется в один клиентский модуль.
  Отдельные файлы `X.hydrate.js`, `X.hydrate_client.js` и `X.ssr.json` на
  каждый компонент удаляются. Один `vela.manifest.json` перечисляет для
  каждого компонента его режим корня и клиентский модуль.

  Go-рендерера и фрагментов (F-2.3, M-5.10).

## 10. Проверка

- **Q-10.1 Шлюз CSR.** Все существующие наборы тестов CSR
  (`runtime_behaviour`, `runtime_nesting_matrix`, тесты кодогенерации,
  браузерные тесты runtime) проходят на блочном движке без изменения
  ожиданий, кроме ожиданий о тексте сгенерированного кода, которые
  заменяются проверками поведения.
- **Q-10.2 Генеративный дифференциальный тест.** Генератор по грамматике
  создаёт шаблоны из всех блоков, возможностей уровня элемента, компонентов,
  слотов и `{#client}` с вложенностью до настраиваемой глубины, плюс
  случайные данные. Для каждого случая строгий браузерный раннер проверяет:
  1. DOM CSR равен DOM, полученному после Go SSR и `hydrate()`
     (нормализованная структура и текст);
  2. гидратация не делает изменений DOM, кроме вставок пустого текста по
     C-4.3 (наблюдается через `MutationObserver`);
  3. усыновлённые узлы сохраняют идентичность;
  4. после каждого шага случайной последовательности обновлений, применённой
     к обеим сторонам, DOM снова равны;
  5. после `destroy()` не остаётся обработчиков, скриптов payload и
     ожидающих колбэков.
  Seed записываются; каждая ошибка становится фиксированным регрессионным
  случаем.
- **Q-10.3 Набор расхождений.** Внедрённые расхождения каждого вида из X-7.1
  в режимах `repair`, `fail` и в production-сборках дают поведение из §7.3,
  включая откат и повторную попытку.
- **Q-10.4 Набор стабильности разбора.** У каждой нормализации и каждого
  отклонения из §5.2 есть положительный или отрицательный случай.
- **Q-10.5 Корпус.** Компоненты `test_projects`, прошедшие трансляцию,
  гидратируются без расхождений.
- **Q-10.6 Отчёт о размере.** Общий объём сгенерированного клиентского кода
  для `test_projects` и `examples` публикуется для старого и блочного
  движков. Это отчёт, а не шлюз.
